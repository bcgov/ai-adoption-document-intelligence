Can PR #244 merge?
Yes — merge it. Both bugs were reproduced in a running browser, the patch was applied to the same tree and both are fixed, with no regression across seven routes plus the workflow editor. One of the three changes is inert and should be cleaned up afterwards, but it is not a blocker.
The two changes that matter (the modal-body scroll fix and the comboboxProps on the Select adapter) were each verified end-to-end with measurements and screenshots, pre- and post-patch, on the same page. The third change — a CSS z-index rule — cannot ever apply, because Mantine writes the dropdown z-index as an inline style. The fix stands without it; the problem is that the PR description credits that rule with doing the work, so it reads as protection that isn't there.

Background

Since 2026-05-22 (commit 4731a47f, 'Add BC DS UI components') the frontend runs two overlay systems side by side: modals are BC Gov Design System Modal, which is React Aria underneath, while dropdowns inside them are still Mantine, because BC DS has no searchable select — the ui/Select adapter falls back to Mantine whenever a caller passes searchable/clearable/allowDeselect/nothingFoundMessage. Neither system knows the other exists. Mantine portals its dropdown to document.body at z-index 300; the BC DS ModalOverlay sits at 1000, so the dropdown painted underneath it — rendered, populated, and completely invisible. Separately, .bcds-modal-body had overflow:hidden and the non-tall modal shell had no max-height, so a long form was clipped rather than scrolled. Nothing regressed to cause this: Create benchmark definition is simply the first form long enough and searchable enough to hit both at once.

What is actually in it

The CSS z-index block is dead code — and the PR body credits it with the fix Not a merge blocker; fix it after

Mantine writes the dropdown z-index as an inline style, and inline beats any stylesheet rule without !important. Proof from the running app with the patch applied: the rule IS present in document.styleSheets, and the /documents Status dropdown, which carries .mantine-Select-dropdown, still computes z-index 300. So the PR body's change #2 — 'Raise Mantine Select/Combobox dropdown stacking above BC DS ModalOverlay' — does not happen. The z-index that matters is the zIndex:1100 inside comboboxProps, which Mantine writes inline. Consequence: MultiSelect, TagsInput and Autocomplete are not covered, and the next person will find a stylesheet rule that looks like it already handles them.

.mantine-Combobox-dropdown,
.mantine-MultiSelect-dropdown {
  z-index: 1100;
}
Added by the PR. Never applies.

A call site already tried this workaround and is silently ignored Pre-existing, but this PR makes it permanent

DocumentValidation.tsx:242 passes comboboxProps={{ zIndex: 10000 }} — someone hit this same stacking problem before and reached for the same lever. It has never worked: pickFieldPassthrough allowlists only data-*, aria-*, id, name, autoComplete, autoFocus, readOnly and placeholder, so comboboxProps is dropped before it reaches Mantine. After this PR the adapter also hardcodes zIndex:1100, so that call site's intent still cannot be expressed.

apps/frontend/src/ui/formFieldUtils.ts:148-160
if (
  key.startsWith("data-") ||
  key.startsWith("aria-") ||
  key === "id" ||
  key === "name" ||
  key === "autoComplete" ||
  key === "autoFocus" ||
  key === "readOnly" ||
  key === "placeholder"
) {
  passthrough[key] = value;
}
comboboxProps is not on the list, so it is silently discarded.
Nothing locks the new behaviour in Minor

Select.test.tsx has a 'uses Mantine fallback when clearable' case but asserts nothing about withinPortal or the floating strategy. One assertion would stop a future refactor from silently reintroducing an invisible dropdown.

overflow-x: hidden on the modal body is an undisclosed clip Minor

Every modal body now clips horizontally with no scrollbar. Nothing in the app is wide enough to hit it that I found, but it is a behaviour change for every modal and it is not in the PR description.

The one place this could bite later: fallback selects inside a Mantine Drawer Latent risk worth knowing

floatingStrategy 'fixed' escapes clipping only while no ancestor establishes a containing block. Mantine's Drawer does both things that break that — its content carries transform: translateX(0) while open (the 'in' state of the slide-* transitions stays applied) and overflow-y: auto. A fallback select inside a drawer would be clipped at the drawer's edge, where before it escaped via the portal. No fallback select is in a drawer today; the sweep found none. That is the failure mode to remember.
