## Task 1 — G-018: the cache must know which activity produced a result

The cache row is keyed `@@unique([workflowLineageId, nodeId, configHash, inputHash])` (`apps/shared/prisma/schema.prisma:899`), where `configHash = sha256Hex(stableJson(getNodeParameters(node)))` (`apps/temporal/src/cache/cached-activity.ts:220`).

**Nothing in that key says which activity the node is.** Change a node from `azureOcr.extract` to `document.classify` and the id, parameters and inputs can all stay the same — so the classifier is served the OCR result for up to 24 h. The preview widget and status badge read the same row, so every surface corroborates the wrong answer.

**The fix is to fold the node's identity-of-computation into `configHash`.** No schema migration: same columns, different hash content. Pre-existing rows simply stop matching and age out on the existing TTL sweep — which is the correct outcome, since we cannot know what activity produced them.

**Files:**
- Modify: `apps/temporal/src/cache/cached-activity.ts:220`
- Test: the existing spec for that module (find it first)

Read `cached-activity.ts` in full — particularly the doc comment at `:5` and `:27` which document the key, and every place `configHash` is computed or returned (it is surfaced in the run-status map as part of `cacheHit`, so its meaning must stay consistent everywhere).

Establish how to get a node's activity identity. `getNodeParameters(node)` exists; find whether there is a matching accessor for the activity type, and how non-activity node types are represented. Do not assume `node.activityType` is always present — check the union in `packages/graph-workflow/src/types.ts:152`.

## Task 2 — G-019: a library workflow cannot vanish under its callers

`workflowRef.workflowId` lives inside `WorkflowVersion.config` JSON, so there is no foreign key. `deleteWorkflow` (`apps/backend-services/src/workflow/workflow.service.ts:958`) catches Prisma `P2003` — which can never fire for a JSON reference. Nothing counts referencing workflows. The parent keeps validating green, and at run time fails with a **retryable** error, so it burns its entire retry budget against something that will never resolve.

- **Reference scan:** `apps/backend-services/src/dynamic-nodes/dynamic-node.repository.ts:395` already does `AND wv.config::text LIKE ${needle}` to find configs referencing a dynamic node before soft-deleting it.

## Notes for the implementer

**G-018 changes a hash, which silently invalidates every existing cache row.** That is intended and is the only safe outcome, but say so in your report and confirm the TTL sweep will clear them — do not add a migration or a manual purge.

**The most likely way to get G-018 wrong** is to include something in the hash that varies between runs for the same computation (a timestamp, an object with unstable key order, a node label). `stableJson` exists for this reason — use it, and keep the hashed payload to identity-of-computation only. A node's *label* must not be in it: renaming a step should not discard its cached work.

**The most likely way to get G-019 wrong** is a scan that misses references or an over-broad `LIKE` that blocks unrelated deletes. Mirror the dynamic-node needle exactly, and test both directions — a real reference blocks, an unrelated workflow does not.

**Do not fix anything outside G-018 and G-019.** In particular: cache TTL length (G-024) is batch 8, and the inline child-graph editor (G-015) is batch 9.
