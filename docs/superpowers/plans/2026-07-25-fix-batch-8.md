1. **The selection doesn't stick.** The page defines `selectNodeSticky` (`WorkflowEditorV2Page.tsx:264`) precisely because a plain `setSelectedNodeId` "doesn't hold — xyflow reasserts its internal (empty) selection". ## Task 3 — G-004: replay must show the graph that ran

Run statuses are matched to nodes **by id** and painted onto whichever config is on screen. Replay never loads the run's own version. Consequences: nodes added since show status they never had; deleted nodes vanish along with their results; stale statuses are never pruned. The version pin is displayed in the run row, which makes it look deliberate.

**Files:** `RunStateContext.tsx`, the run-history/replay entry points, the version-fetch path, specs.

- [ ] **Step 1: Establish what identifies a run's version**

`RunSummaryDto.workflowVersionId` exists (`list-runs.dto.ts:128`). Find how to load that version's config — the workflow service already resolves versions for other features; reuse it.

- [ ] **Step 2: Write failing tests**

```ts
it("loads the run's own version when replaying", () => {});
it("does not paint statuses for nodes absent from the replayed version", () => {});
it("clears a previous replay's statuses when leaving replay", () => {});
it("shows the live config when not replaying", () => {});
```

- [ ] **Step 3: Run, watch fail.**

- [ ] **Step 4: Implement**

Load the run's version on entering replay and render statuses against it. **Make it obvious the canvas is showing a historical version** — an author who cannot tell which graph they are looking at has the same problem in a new form.

**Do not make replay silently mutate the editing config.** Replay is a view. If the author has unsaved edits, entering and leaving replay must not lose them — batch 5 added undo and an unsaved guard; do not undermine them. State how you handled this.

- [ ] **Step 5: Green + commit**

## Task 4 — G-024: yesterday's run has nothing left to show

`DEFAULT_CACHE_TTL_MS = 24 h` (`packages/graph-workflow/src/cache/constants.ts:11`) and the sweep deletes expired rows. "The run happened yesterday" is the most common debugging situation there is, and it lands exactly on the boundary.

The offered remedy compounds it: the **Re-run** button POSTs with no `workflowVersionId`, i.e. against current head — which after Task 3 is visibly the wrong graph — and appears in history as a new official result.

**This task needs a judgement call, not just code.** Extending the TTL trades storage for retention.

- [ ] **Step 1: Establish the real cost**

Measure. How large is a cached row in practice, how many rows does a run produce, what is the table's current size? **Report actual numbers before proposing a TTL.** A recommendation without them is a guess.

- [ ] **Step 2: Propose, then implement**

Options worth weighing: a longer default; a shorter TTL for previews but longer for the last run of a workflow; retaining the most recent N runs regardless of age. **Say which you chose and why, in the code and your report.**

Make the TTL configurable via environment rather than a hard-coded constant, so this is tunable without a deploy.

- [ ] **Step 3: Fix the Re-run button's target**

It must re-run **the version being replayed**, not head. Pass the `workflowVersionId`. If re-running a historical version is not supported, say so in the UI instead of silently running a different graph.

- [ ] **Step 4: Tests**

```ts

it("honours a configured TTL", () => {});
it("keeps the configured retention for a run that would previously have expired", () => {});
```

- [ ] **Step 5: Green + commit**

