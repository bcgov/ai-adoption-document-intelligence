## Task 1 — G-020: human review can never resume a workflow

**The headline HITL capability is broken end to end.** A workflow hits a human gate, the document reaches the review queue, a reviewer approves it — and the workflow keeps waiting until it times out an hour later and fails.

**Two independent breaks, either one fatal on its own.** Both are confirmed:

1. **The approve action never signals Temporal.** `apps/backend-services/src/hitl/hitl.service.ts:393` `approveSession` updates the review session to `approved`, sets the document to `complete`, releases the lock and records an audit event. It never calls `sendHumanApproval`. The workflow is not told anything.
2. **The run id is never persisted.** `TemporalClientService.sendHumanApproval` exists and works, and `document.controller.ts:839` calls it — but it reads `document.workflow_execution_id || document.workflow_id`, and `workflow_execution_id` is written as **`null`** at every creation site: `document.service.ts:233`, `document.service.ts:267`, `workflow.controller.ts:724`. So the one endpoint that does signal always throws `BadRequestException`.

**Files:**
- Modify: `apps/backend-services/src/document/document.service.ts` (~`:233`, `:267`)
- Modify: `apps/backend-services/src/workflow/workflow.controller.ts` (~`:724`)
- Modify: `apps/backend-services/src/hitl/hitl.service.ts` (`approveSession` ~`:393`)
- Tests: the specs beside each

- [ ] **Step 1: Read first**

Read `approveSession` in full, and the `sendHumanApproval` path in `document.controller.ts:~820-860` — it already does the right thing, including audit. Read `TemporalClientService.sendHumanApproval` (`temporal-client.service.ts:1008`) and note the signal name it sends: `humanApproval`. Batch 1 made the palette default match that name, so a gate authored today is resumable **if** the signal is sent.

Establish where a document first learns its run id. The three `null` sites are creation-time; find where the run actually starts and what identifier is available there.

- [ ] **Step 2: Write the failing tests — persistence half**

```ts
it("persists the workflow execution id when a run starts for a document", async () => {});
it("leaves workflow_execution_id null when no run was started", async () => {});
```

- [ ] **Step 3: Write the failing tests — signal half**

```ts
it("sends a humanApproval signal when a review session is approved", async () => {});
it("does not fail the approval when the workflow is already gone", async () => {});
it("records an audit event for the signal", async () => {});
```

The second matters: a run may have timed out or been cancelled before the reviewer got there. **Approving must still succeed and still mark the document complete** — a dead workflow is not a reason to reject the reviewer's decision. Decide the behaviour (log and continue is the sensible answer), implement it, and assert it.

- [ ] **Step 4: Run both, watch them fail.**

```bash
npm test -w apps/backend-services -- hitl.service document.service 2>&1 | tail -20
```

- [ ] **Step 5: Implement persistence**

Write the run id onto the document when the run starts. Do not simply stop writing `null` at creation — creation genuinely has no run yet. The fix is an update at run-start.

- [ ] **Step 6: Implement the signal**

In `approveSession`, send `humanApproval` before or alongside the status transition, carrying the reviewer's decision. Mirror the payload shape `document.controller.ts:839` already sends (`approved`, `reviewer`, `comments`, `rejectionReason`, `annotations`) so a gate sees one consistent shape regardless of which surface approved it.

**Follow the repo's transaction/audit rules.** The session update, document transition and lock release must stay consistent; the signal is an external call and must not sit inside a Prisma transaction — send it after the commit, and make its failure non-fatal per Step 3.

**Rejection matters too.** If there is a `rejectSession` counterpart, it has the same gap — check, and fix it the same way. Report what you find.

- [ ] **Step 7: Green + commit**

```bash
npm test -w apps/backend-services -- hitl document 2>&1 | tail -12
npm run -w apps/backend-services type-check 2>&1 | tail -5
git add apps/backend-services/src
git commit -m "fix(hitl): approving a review actually resumes the waiting workflow (G-020)"
```

## Task 2 — G-008: renaming a variable must rename it everywhere

`renameCtxKey` (`apps/frontend/src/features/workflow-builder/settings/rename-ctx-key.ts`) rewrites shared `inputs`/`outputs` bindings and has explicit cases for `map`, `join`, `childWorkflow`, `switch` and `pollUntil`.

**There is no `source` case** — and source nodes produce ctx keys. The rename dialog states it updates all references; it does not, and it does not say which it skipped.

**Files:**
- Modify: `apps/frontend/src/features/workflow-builder/settings/rename-ctx-key.ts`
- Test: its spec

- [ ] **Step 1: Establish the full reference surface**

`packages/graph-workflow/src/auto-wire/ctx-source.ts` has `nodeTypeCtxWrites` — the enumeration of what every node type writes, derived from the executors and hardened across batches 2 and 4. **Use it as the checklist.** For every writer it lists, confirm `renameCtxKey` handles it. Report the full audit, not just the source gap.

Also check the childWorkflow **library port paths** the register names — `inputMappings` / `outputMappings` port paths — and whether they are covered by the existing `childWorkflow` case or only partially.

- [ ] **Step 2: Write failing tests, one per uncovered writer**

```ts
it("renames a key produced by a source node", () => {});
it("renames a childWorkflow input mapping port path", () => {});
it("renames a childWorkflow output mapping port path", () => {});
// plus one per any other gap the Step 1 audit finds
```

- [ ] **Step 3: Run, watch fail.**

- [ ] **Step 4: Implement the missing cases.**

- [ ] **Step 5: Prove completeness structurally**

Add a test that fails if a new node type is added to the union without a rename case — an exhaustive switch, or a test iterating `nodeTypeCtxWrites`'s known types and asserting each is handled. **This is the regression floor: the bug was a missing case, so the guard must be about missing cases, not about the specific one we fixed.**

## Notes for the implementer

**G-020 is two fixes, and fixing one alone leaves the feature broken.** Do not stop after the signal call — without the persisted run id there is nothing to signal. Verify both halves.

**Do not make a dead workflow block an approval.** The reviewer's decision is the record of truth; a missing or completed workflow is a logging concern, not a rejection.

**G-008's real bug is "a case was missing", not "the source case was missing".** The guard in Step 5 is the more valuable half of that task.

**Do not fix anything outside G-020 and G-008.** Previews (G-011/G-022) are batch 7; replay and run history (G-004/G-024/G-014/G-010) are batch 8.
