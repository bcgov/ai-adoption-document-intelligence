> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Stop the editor losing work. Add undo/redo, guard against leaving with unsaved changes, and retire the blocking delete confirmation that only exists because undo was missing.

**Architecture:** One history stack wrapping the single `config` state. Every mutation already flows through one setter, so the choke point exists. The unsaved guard reuses the dirty bit the page already computes.

## What is already true

- `config` is a single `useState<GraphWorkflowConfig>` at `WorkflowEditorV2Page.tsx:176`. **9** `setConfig` call sites in the page; **11** `onConfigChange` calls in the canvas, all of which flow into it. One choke point.
- **Node drags already coalesce.** `handleNodeDragStop` persists final positions once, at drag end — so a drag is naturally one undo step. Do not add debouncing for it.
- **A dirty bit already exists**, as a reference compare: `configRef.current !== lastHydratedConfigRef.current` (`~:513`). It exists to stop server refetches stomping unsaved edits, and `handleSave` re-baselines it. G-027 reuses it rather than inventing a second notion of dirty.
- **There is no keyboard shortcut infrastructure anywhere in the feature.** No `useHotkeys`, no key handlers. You are adding the first.

- [ ] **Step 3: Run, watch fail.**

- [ ] **Step 4: Implement the hook**

```ts
export function useConfigHistory(initial: GraphWorkflowConfig): {
  config: GraphWorkflowConfig;
  setConfig: (updater: GraphWorkflowConfig | ((prev: GraphWorkflowConfig) => GraphWorkflowConfig)) => void;
  /** Replace state WITHOUT recording history — initial load, hydration, save re-baseline. */
  resetConfig: (next: GraphWorkflowConfig) => void;
  undo: () => void;
  redo: () => void;
  canUndo: boolean;
  canRedo: boolean;
};
```

The two-setter split is the important design decision: `setConfig` records, `resetConfig` does not. Anything else leaks lifecycle churn into the undo stack.

- [ ] **Step 5: Adopt it in the page**

Replace `useState` with the hook. Route each of the 9 call sites to `setConfig` or `resetConfig` deliberately — **decide each one and say which in your report.** Hydration and initial load are `resetConfig`; user edits are `setConfig`.

**Do not break the hydration guard.** It compares `configRef.current` against `lastHydratedConfigRef.current` by reference. Undo produces a config object that is not the hydrated one, so the page correctly continues to treat it as a local edit — verify this rather than assuming.

- [ ] **Step 6: Keyboard + UI**

Bind Ctrl/Cmd+Z to undo and both Ctrl/Cmd+Shift+Z and Ctrl+Y to redo, scoped to the editor and **ignored while focus is in a text input, textarea or contenteditable** — otherwise you break native text undo inside every settings field. Test that explicitly.

Add visible Undo/Redo controls near the existing top-bar actions, disabled when the stack is empty. A keyboard-only feature is undiscoverable, which is a gap of the same family as the ones this effort exists to close.

## Notes for the implementer

**The two-setter split is the whole design.** If lifecycle updates leak into the history stack, undo will walk backwards through hydration and auto-layout and feel broken. Be deliberate about all 9 call sites.

**Do not break text editing.** Undo bound globally will hijack Ctrl+Z inside every settings text field. Scope it and test it.

**Undo must restore pruned ctx declarations.** Batch 2 made node deletion prune `config.ctx`. If undo restores the node but not its declarations, we have replaced one silent-data-loss bug with another.

**Do not fix anything outside G-003, G-027 and the delete-toast conversion.** Find-a-node (G-009) is batch 9; previews (G-011/G-022) are batch 7.
