## Fix 1 — C-071: raw NUL bytes break search on the canvas file

Two literal NUL bytes sit in a template literal at `WorkflowEditorCanvas.tsx:2745`. Someone used NUL as a field separator and typed the byte instead of the escape. Consequence: every grep-based tool silently sees a binary file.

**Files:**
- Modify: `apps/frontend/src/features/workflow-builder/canvas/WorkflowEditorCanvas.tsx:2745`

- [ ] **Step 1: Confirm the defect**

```bash
python3 -c "
d=open('apps/frontend/src/features/workflow-builder/canvas/WorkflowEditorCanvas.tsx','rb').read()
print('NUL count:', d.count(b'\x00'))
print('grep sees binary:', __import__('subprocess').run(['grep','-c','dataWireSig','apps/frontend/src/features/workflow-builder/canvas/WorkflowEditorCanvas.tsx'],capture_output=True).stdout)
"
```

Expected: `NUL count: 2` and an empty grep result.

- [ ] **Step 2: Replace the raw bytes with escape sequences**

The line currently reads (with `<NUL>` standing for the raw byte):

```ts
      const dataWireSig = (wire: DataWire) =>
        `${wire.source}<NUL>${wire.target}<NUL>${wire.targetPort}`;
```

Rewrite it so the separator is the escape `\0`, which produces the identical runtime string:

```ts
      const dataWireSig = (wire: DataWire) =>
        `${wire.source}\0${wire.target}\0${wire.targetPort}`;
```

Use a byte-level edit (Python) rather than an editor round-trip, so no other byte in this 119 KB file changes:

```bash
python3 -c "
p='apps/frontend/src/features/workflow-builder/canvas/WorkflowEditorCanvas.tsx'
d=open(p,'rb').read()
assert d.count(b'\x00')==2, d.count(b'\x00')
d=d.replace(b'\x00', b'\\\\0')
open(p,'wb').write(d)
print('replaced')
"
```

- [ ] **Step 3: Verify the file is no longer binary and the string is unchanged**

```bash
python3 -c "
d=open('apps/frontend/src/features/workflow-builder/canvas/WorkflowEditorCanvas.tsx','rb').read()
print('NUL count now:', d.count(b'\x00'))
"
grep -c "dataWireSig" apps/frontend/src/features/workflow-builder/canvas/WorkflowEditorCanvas.tsx
git diff --stat apps/frontend/src/features/workflow-builder/canvas/WorkflowEditorCanvas.tsx
```

Expected: NUL count `0`; grep returns `2` (not silence); diff touches **1 file, 1 insertion, 1 deletion**. If the diff is larger, the editor reformatted something — revert and redo with the byte-level edit.

- [ ] **Step 4: Typecheck + run the canvas tests**

```bash
npm run -w apps/frontend typecheck 2>&1 | tail -5
npx vitest run --root apps/frontend src/features/workflow-builder/canvas 2>&1 | tail -15
```

Expected: typecheck clean; canvas suite passes. (`\0` and a raw NUL are the same string at runtime, so no test should change behaviour.)

- [ ] **Step 5: Commit**


## Fix 2 — G-017: human gates ship a signal name that can never work

A human gate pauses until a signal naming that gate arrives. Three problems:

1. The palette skeleton ships `signal: { name: "" }`, so a freshly dropped gate saves clean and creates a gate nothing can ever open.
2. Nothing validates the name — no `signal` path appears anywhere in the validator.
3. The settings form offers four autocomplete presets, but the only name anything in this system sends is `humanApproval` (`temporal-client.service.ts:1022`). Picking `approve`, `review` or `reject` from the product's own suggestion list produces an unopenable gate.

Free-typed names must stay legal — an external system may signal a gate with its own name. The fix is to stop *suggesting* names nothing sends, and to stop shipping an empty one.

**Files:**
- Modify: `apps/frontend/src/features/workflow-builder/palette/control-flow-skeletons.ts:112`
- Modify: `apps/frontend/src/features/workflow-builder/settings/control-flow/HumanGateNodeSettings.tsx:90`
- Modify: `packages/graph-workflow/src/validator/validator.ts`
- Test: `packages/graph-workflow/src/validator/validator.test.ts` (or the existing humanGate validator spec — find it first)

## Fix 3 — G-021: starting any run cancels every other run of that workflow

Both run-start paths call `TemporalClientService.cancelInFlightTriesForLineage` before starting. That helper asks Temporal for *every running execution in the lineage* — `WorkflowLineageId = "<id>" AND ExecutionStatus = "Running"` — with nothing distinguishing an editor preview ("Try") from a production run. So a second production run cancels the first.

The intent is stated correctly in the call-site comment and in the helper's own name: cancel in-flight **Tries**. Only the query is wrong. The fix is to give runs a trigger and filter on it.

**Files:**
- Modify: `apps/backend-services/src/temporal/temporal-client.service.ts` (search-attribute list ~`:74-85`; `startGraphWorkflow` `:253`; `searchAttributes` construction `:291`; `listRunningInLineage` `:675`; `cancelInFlightTriesForLineage` `:913`)
- Modify: `apps/backend-services/src/workflow/workflow.controller.ts:534` (API `startRun`) and `:728` (upload-and-Try)
- Test: `apps/backend-services/src/temporal/temporal-client.service.spec.ts`

- [ ] **Step 1: Read before changing**

Read `temporal-client.service.ts:74-90` (the `SEARCH_ATTRIBUTES` list and how `ensureSearchAttributes` registers them), `:253-350` (`startGraphWorkflow` and its `searchAttributes` object), and `:675-695` + `:913-945` (the list/cancel helpers). Confirm how attributes are registered against the cluster before adding one.

- [ ] **Step 2: Write the failing tests**

In `temporal-client.service.spec.ts`, add a describe covering the new behaviour:

```ts
it("only cancels runs explicitly marked as tries", async () => {

});

  // assert startGraphWorkflow passes RunTrigger: ["try"] / ["api"] through
});
```

Follow the spec file's existing mocking style for the Temporal client — read it first; do not invent a new harness.

- [ ] **Step 4: Add the `RunTrigger` search attribute**

Add `{ name: "RunTrigger" }` to the `SEARCH_ATTRIBUTES` list with a comment explaining it distinguishes an editor preview from a production run, and that the cancel-on-new-Try helper filters on it.

- [ ] **Step 5: Thread the trigger through `startGraphWorkflow`**

Add a required parameter — do not default it, so every call site makes an explicit choice:

```ts
export type RunTrigger = "try" | "api";
```

Add it to the signature and set `RunTrigger: [trigger]` in **both** branches of the `searchAttributes` object (doc-mode and adhoc-mode).

- [ ] **Step 6: Filter the cancel query**

Change the query used by `cancelInFlightTriesForLineage` so it selects only tries:

```ts
const query = `WorkflowLineageId = "${workflowLineageId}" AND ExecutionStatus = "Running" AND RunTrigger = "try"`;
```

Keep the general-purpose `listRunningInLineage` intact if other callers use it — check first with `grep -rn "listRunningInLineage" apps/`. If the cancel helper is its only caller, narrowing it in place is fine; otherwise add a narrowed variant and leave the general one alone.

**Migration note to put in a code comment:** runs started before this change carry no `RunTrigger`, so they will not match `RunTrigger = "try"` and will no longer be cancelled. That is the safe direction — an unknown run is treated as production.

- [ ] **Step 7: Update both call sites**

- `workflow.controller.ts:534` — the API `startRun` path passes `"api"`.
- `workflow.controller.ts:728` — the upload-and-Try path passes `"try"`.

Both keep calling `cancelInFlightTriesForLineage`, which now genuinely only cancels tries. Update the comment at `:527-531` — it currently claims every new run wins over a stale in-flight one, which is no longer (and should never have been) true for production runs.
