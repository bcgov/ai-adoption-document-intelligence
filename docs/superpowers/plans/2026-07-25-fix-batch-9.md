## Task 1 — G-016: `pollUntil` loses every activity affordance

A `pollUntil` node wraps a real activity, but renders through the **control-flow rectangle** path. `rendersPerPortHandle` (`canvas/port-rows.ts:206`) returns false for anything but `activity`, and `estimateNodeHeight` sizes it as a rectangle — while `computePortRows` and `resolveWireableInputRows` both accept it. So its inputs appear in the settings panel and in the problems badge but **there is nothing on the canvas to drag to.** Two surfaces, one node type, opposite answers.

The same rectangle path never consults the activity catalog, so when the wrapped activity type disappears the card looks entirely normal — where an `activity` degrades legibly (`❓`, "Unregistered activity.", the raw type) and a `dyn.*` node gets a red "Deleted" badge.

**Cheapest fix in the batch — do it first.**

```ts

it("sizes a pollUntil card from its port rows, not as a rectangle", () => {});
it("degrades legibly when a pollUntil's wrapped activity is unregistered", () => {});
it("still renders switch/map/join as control-flow rectangles", () => {});
```

- [x] **Step 2: Run, watch fail. Step 3: Implement. Step 4: Green + commit**

```bash
git commit -am "fix(workflow-builder): pollUntil gets the port handles and catalog fallback every activity has (G-016)"
```

## Task 2 — G-009: you cannot find a node, or ask what uses a value

There is no search for nodes. The only search box searches the **palette** — the catalog of things you can add, not your workflow. And there is no way to ask "what else reads this variable?" before changing it.

Invisible at 5 nodes. The master template is 16. Real workflows exceed 40.

- [x] **Step 1: Write failing tests**

```ts
it("finds nodes by label", () => {});
it("finds nodes by activity type", () => {});
it("selects and reveals the chosen result", () => {});
it("reports what reads a given ctx variable", () => {});
it("reports what writes it", () => {});
it("says so when nothing references it", () => {});
```

- [x] **Step 2: Implement find-a-node**

A search affordance scoped to the current graph, matching label and activity type. Selecting a result must **select and reveal** it — batch 8 added `selectNodeSticky` and `revealNodes()` for exactly this. Reuse them; do not add a third selection mechanism.

- [x] **Step 3: Implement references-to-a-variable**

"What reads this?" is answerable from data that already exists: `nodeTypeCtxWrites` (`packages/graph-workflow/src/auto-wire/ctx-source.ts`) enumerates writers, and `resolveCtxKeySource` already answers the producer half. Build the reader half beside them and surface both wherever a variable is shown (the settings drawer's ctx list is the natural home).

**This is also the safety net for renaming and deleting** — batch 2 made deletion prune declarations and batch 6 fixed the rename sweep, but an author still can't see the blast radius *before* acting.

- [x] **Step 4: Green + commit**

```bash
git commit -am "feat(workflow-builder): find a node, and see what reads a variable (G-009)"
```

## Task 3 — G-015: an inline sub-workflow is a rules-free hole

`workflowRef.type === "inline"` embeds a **complete `GraphWorkflowConfig`**, and the entire editing surface for it is a JSON `Textarea` (`settings/control-flow/ChildWorkflowNodeSettings.tsx:266`) with the hint "Edit the inline child graph as JSON".

Inside that textarea there is no palette, no canvas, no port rows, no auto-wire, no kind checking, no preview and — the part that matters most — **no validation**. The validator never descends into `workflowRef.inline`; there is only a doc comment at `validator.ts:~1238`. Every rule the product enforces is dropped one level down.

**Scope this deliberately.** A nested visual editor is disproportionate and is not what this batch is for. **The goal is that the inline graph obeys the same rules and reports the same problems as the outer one** — not that it gets its own canvas.

- [x] **Step 1: Make the validator descend**

Validate `workflowRef.inline` with the same rules as the top-level config, and anchor its errors so they identify both the parent node and the inner node — e.g. `nodes.<parentId>.inline.nodes.<childId>.…`.

Decide and document how inner errors surface: they must reach the top-bar count and the drawer, or they are invisible again. Batch 8's `anchor-target.ts` resolves anchors to navigation targets — extend it so an inner error at least selects the parent node rather than falling to workflow-level.

- [x] **Step 2: Write failing tests**

```ts
it("reports an invalid inline child graph", () => {});
it("anchors an inline error to both the parent node and the inner node", () => {});
it("does not report a valid inline child graph", () => {});
it("surfaces an inline error in the drawer and the top-bar count", () => {});
```

- [x] **Step 3: Make the textarea honest**

Keep the JSON editor — replacing it is out of scope — but it must show validation results rather than only parse errors. A textarea that accepts a structurally-invalid graph in silence is the defect.

- [x] **Step 4: Green + commit**

## Notes for the implementer

**Order: G-016, then G-009, then G-015.** Cheapest first, and G-009's reveal behaviour depends on batch 8's helpers already existing.

**Do not build a nested visual editor.** G-015 is about the inline graph obeying the same *rules*, not getting the same *UI*. If you find yourself building a second canvas, stop.

**Reuse, don't reinvent.** `selectNodeSticky` and `revealNodes()` (batch 8), `nodeTypeCtxWrites` and `resolveCtxKeySource` (batches 2 and 4), and `anchor-target.ts` (batch 8) all exist because earlier batches built them. A third selection mechanism or a second producer enumeration would be a regression in itself.
