# Fix Batch 4 — The Authoring Model

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make error handling authorable, give control-flow and source nodes declared outputs, and stop one failed map branch destroying the others.

**Architecture:** Three fixes in dependency order. G-007 declares what control-flow nodes produce; G-001 adds the settings surface for a policy the engine already honours; G-026 uses that policy to decide what a partial map result means.

**Tech Stack:** TypeScript, React (Mantine), Vitest (frontend), Jest (temporal / graph-workflow).

**Source:** G-001, G-007, G-026 in [GAP_REGISTER.md](../../../feature-docs/20260724-workflow-builder-spec-completion/GAP_REGISTER.md)

## What is already true — read before planning any work

Two agents disagreed about this and one was wrong. The settled facts:

- **The engine DOES honour `errorPolicy`.** `apps/temporal/src/graph-engine/error-handling.ts` reads `onError` (`:24`), `fallbackEdgeId` (`:37`) and `retryable` (`:76`).
- **The validator already enforces it** — `validator.ts:336` errors when `onError: "fallback"` has no `fallbackEdgeId`.
- **The canvas already renders the error handle**, gated on `errorPolicy?.onError === "fallback"` (`WorkflowEditorCanvas.tsx:592`, handle at `:663`/`:856`).
- **`EdgePicker` already exists** and its own doc comment names `errorPolicy.fallbackEdgeId` as a use case (`graph-widgets/EdgePicker.tsx:13`) — it is simply never mounted for it. Mount sites today: `SwitchNodeSettings.tsx:174`/`:256`, `HumanGateNodeSettings.tsx:207`.

**So G-001 is purely a missing authoring surface.** Do not build engine support, validator rules, or canvas handles — they exist. Build the form, and wire the edge.

## Task 3 — G-026: one bad branch must not destroy the rest

`executeWithConcurrencyLimit` (`apps/temporal/src/graph-engine/runner-utils.ts`) rejects on the first failure in **two** places — `Promise.race(executing)` inside the loop and `Promise.all(executing)` at the end. One failed branch discards every sibling result.

**This is the fix that needed G-001 first**, because "keep going when a branch fails" is a policy the author has to be able to express — and `onError: "skip"` is now expressible.

**Files:**
- Modify: `apps/temporal/src/graph-engine/runner-utils.ts`
- Modify: `apps/temporal/src/graph-engine/node-executors.ts` (the map executor at `:603`)
- Test: `apps/temporal/src/graph-engine/runner-utils.test.ts`

- [ ] **Step 1: Write failing tests**

```ts
it("returns every successful result when one item fails", () => { });
it("reports which indices failed, with their errors", () => { });
it("still respects the concurrency limit when failures occur", () => { });
it("surfaces the failure to the caller rather than swallowing it", () => { });
```

- [ ] **Step 2: Run, watch fail** — expect a rejection that loses the sibling results.

- [ ] **Step 3: Change the helper to settle, not reject**

Collect a per-item outcome (`{ status, value }` / `{ status, reason, index }`) instead of rejecting. **The helper must not decide policy** — it returns outcomes; the map executor decides what to do with them.

Keep the concurrency limiting intact: `Promise.race` on a rejected promise also rejects, so the in-loop wait needs the same treatment.

- [ ] **Step 4: Apply the policy in the map executor**

At `node-executors.ts:603`, decide from the map node's `errorPolicy.onError`:

- **`fail` (default, and the behaviour when no policy is set)** — throw, preserving today's semantics, but include which branches failed in the message. Successful results stay in `state.mapBranchResults` so a downstream join can see what did complete.
- **`skip`** — keep the successful results, record the failures, continue.
- **`fallback`** — out of scope for a map body; treat as `fail` and say so in a comment.

**Default must remain `fail`.** This fix is about not *destroying* the siblings, not about silently changing what a workflow does. A workflow with no error policy must behave as it does today, except that the surviving results are retained.

- [ ] **Step 5: Check the join**

`executeJoinNode` reads `state.mapBranchResults`. Decide and document what a join receives when some branches failed under `skip` — the successful subset, in original index order, is the sensible answer. Add a test.

## Notes for the implementer

**Order matters here.** G-007 first (declares outputs), then G-001 (the policy surface), then G-026 (which consumes the policy). Do not reorder.

**G-007 is the riskiest of the three** because it changes auto-wiring behaviour across every existing workflow. More producers means more auto-binding — and more potential ambiguity. Expect test churn, and treat every change as a real behaviour change to report rather than a fixture to silence.

**Do not change default behaviour in G-026.** A workflow with no error policy must do exactly what it does today, except that surviving branch results are retained rather than discarded.

**Do not fix anything outside G-001, G-007, G-026.** Undo (G-003) is batch 5; preview coverage (G-011/G-022) is batch 7; the inline child-graph editor (G-015) is batch 9.
