From Zero to Integration

This step-by-step tutorial is for a developer on an outside team who wants to send documents to the Document Intelligence Platform (DIP) and get extracted data back. It starts from nothing and assumes your application and DIP run on different machines and networks. Your app talks to DIP only over HTTPS with an API key. You don't need any DIP-specific code or libraries.

Each step uses curl, so you can confirm every call works from the machine that will host your integration before you write any code. The last step explains how to move the same calls into your own service, in any language.

How It Works

An integration makes four kinds of calls. Processing runs in the background after the upload, so your app pulls status and results. DIP never needs inbound access to your network.

1. Discover

GET /api/models
GET /api/workflows

Optional. See which models and workflows your key can use.

2. Upload

POST /api/upload

Send a base64 file and a workflow slug. Get back a document id.

3. Poll

GET /api/documents/{id}

Check the status every few seconds until it is final.

4. Fetch Result

GET /api/documents/{id}/ocr

Read the extracted fields and text.

Before You Start

What Why
A DIP group Documents, workflows, and API keys all belong to a group.
An API key for that group Server-to-server authentication through the x-api-key header.
A workflow slug in that group Every upload must name a workflow. The workflow defines the processing steps.
The <DIP_API_URL> for your target environment Supplied by the DIP team.
Network reachability from your server to <DIP_API_URL> over HTTPS (443) See Step 2. Production DIP only accepts callers from an IP allow-list.

Step 1: Get Access and an API Key

  1. Sign in — In a browser, go to <DIP_UI_URL> and sign in with your Keycloak/IDIR account.
  2. Join a group — Ask to join a group, or have a DIP admin add you. Only a group ADMIN can create API keys. If you aren't an admin, ask your group admin to generate the key and share it with you securely.
  3. Generate the key — Go to Settings → API key → Generate API key. Copy the key right away. It is shown only once, because DIP stores only a hash.
  4. Note your group id — You need it only to list workflows; uploads infer the group from the key. Open Groups in the DIP UI and click your group. The id is the last part of the page URL (<DIP_UI_URL>/groups/<group id>). It is also returned as groupId when the key is generated.
  5. Store the key — Put it in your application's secret store (for example a vault or a Kubernetes/OpenShift secret). Don't store it in source code.
One key per group, per environment. Regenerate key replaces the group's key, so the old key stops working immediately. Repeat this step in each DIP environment you integrate with.

Step 2: Check the Network Path

Run the commands in this tutorial from the machine (or a machine on the same network) that will host your integration. That confirms the network path works before you write any code. Set these variables first:

export DIP=<DIP_API_URL>
export KEY=<your api key>
export GROUP=<your group id>

DIP is deployed as OpenShift routes behind an HAProxy router. Confirm the details for your target environment with the DIP team.

Network and hosting considerations
Topic What to know
HTTPS only DIP routes terminate TLS at the edge and redirect plain HTTP to HTTPS. Always call https://…. A redirected POST can arrive as a GET or lose its body, which looks like a confusing 404/400. This doesn't apply if your app shares a network with DIP and calls the backend directly (for example http://localhost:3002 or the in-cluster service).
Production IP allow-list The production backend route only accepts connections from BC Government public address ranges (142.22.0.0/16 – 142.36.0.0/16). That includes the gov VPN and the OpenShift Silver/Gold/Gold-DR egress pools. If your app is hosted elsewhere (for example a public cloud or a vendor network), requests are refused before they reach DIP.
Your own egress Make sure your firewall or cluster egress policy (for example an OpenShift NetworkPolicy or an egress firewall) allows outbound HTTPS to the DIP host.
Rate limits count your public IP 100 requests / 60 s globally, and 20 failed API-key attempts / 60 s. If several of your services or pods share one NAT egress IP, they share these limits.
Request size The DIP API accepts JSON bodies up to 50 MB. Base64 adds about 33%, so the practical file limit is about 37 MB.
Timeouts The upload call converts the file to PDF before it responds, so give uploads a generous client timeout (60 s or more). OpenShift routes time out idle requests at 30 s by default unless DIP has configured otherwise. All other calls are quick.
No callbacks DIP doesn't push results or webhooks. Your app pulls status and results.
File retention A workflow may purge stored files after processing. After a purge, /view and /download return 410 Gone, but /ocr still returns the extracted result. Keep your own copy of the original file if you need it.

Step 3: Check Your Key and Pick a Workflow

The first call checks connectivity and the key at the same time. The second lists the workflows you can upload to.

# Models (Azure prebuilt + models your group trained)
curl -s -H "x-api-key: $KEY" $DIP/api/models

# Workflows in your group (slug, name, config)
curl -s -H "x-api-key: $KEY" "$DIP/api/workflows?groupId=$GROUP"
Reading the result
If the first call hangs or the connection is refused, it's a network problem (see Step 2). A 401 means you reached DIP but the key is wrong.

Pick a workflow slug from the list. Workflows are created by DIP users in your group, so the names vary by group and environment. A typical DIP instance includes something like:

slug Notes
standard-ocr Azure Document Intelligence OCR → cleanup → confidence check → optional human review. A good starting point.
standard-ocr-mistral Same pipeline using Mistral OCR.
multi-page-report Splits multi-page reports by keyword.

Each workflow has a default model (config.ctx.modelId.defaultValue). You can override it for each upload with model_id. For example, prebuilt-layout extracts generic text and structure from any document. Ask your group's DIP admin which workflow and model fit your documents.

Step 4: Upload a Document

Send POST /api/upload with a JSON body. The file field is the file content base64-encoded. Writing the body to a file avoids shell argument-length limits for larger documents.

B64=$(base64 -w0 invoice.pdf)
cat > body.json <<EOF
{
  "title": "Invoice 123",
  "file": "$B64",
  "file_type": "pdf",
  "original_filename": "invoice.pdf",
  "workflow_slug": "standard-ocr",
  "model_id": "prebuilt-layout",
  "metadata": { "externalRef": "my-system-123" }
}
EOF

curl -s -X POST $DIP/api/upload \
  -H "x-api-key: $KEY" -H "content-type: application/json" \
  --max-time 120 \
  --data @body.json

Response 201:

{ "success": true,
  "document": { "id": "652946b5-...", "title": "Invoice 123", "status": "pre_ocr",
                "file_type": "pdf", "file_size": 668, "created_at": "..." } }
Save document.id in your own system. You need it for every later call. Because processing continues after the upload returns, your app can restart and resume polling later with the saved id.

For every upload field, including workflow_version and ctx_overrides, see Upload Request Fields in the Integrations Guide.

Step 5: Poll Until the Status Is Final

curl -s -H "x-api-key: $KEY" $DIP/api/documents/<id>

Stop polling when status is final: complete, awaiting_review, failed, conversion_failed, or rejected. awaiting_review means a person must review the document, but the result is already readable. See Document Statuses for what each status means.

Poll every 3–5 seconds, and stop after a reasonable timeout. A single page usually finishes in seconds, but it can take longer when DIP is busy. Remember that the rate limit is shared per public IP (see Step 2).

Step 6: Get the Result

curl -s -H "x-api-key: $KEY" $DIP/api/documents/<id>/ocr
{
  "document_id": "652946b5-...",
  "status": "complete",
  "model_id": "prebuilt-layout",
  "ocr_result": {
    "keyValuePairs": { ... },              // extracted fields (custom/form models)
    "content": {
      "format": "text",
      "text": "full document text ...",
      "pages": [ { "pageNumber": 1, "content": "...", "lines": [ ... ] } ]
    },
    "processed_at": "..."
  }
}

Custom or Trained Models

Read the field values from ocr_result.keyValuePairs.

Prebuilt Read / Layout

Read ocr_result.content.text and content.pages.

Step 7: Move It Into Your Service

Once each curl call works, your service makes the same HTTPS calls with any HTTP client. No DIP library is needed.

In your service What to do
Configuration Provide <DIP_API_URL>, the API key, and the workflow slug as environment variables from your secret store. Send the key in the x-api-key header on every call.
Upload Base64-encode the file, call POST /api/upload (Step 4) with a generous client timeout, and save document.id with your own record.
Poll Call GET /api/documents/{id} every 3–5 seconds until the status is final (Step 5), with an overall timeout.
Read the result Unless the status is failed or conversion_failed, call GET /api/documents/{id}/ocr (Step 6) and store what you need.
Errors Treat non-2xx responses as errors and log the response's message, never the API key. See Troubleshooting.

In a long-running service, consider polling from a background job keyed on the saved document id rather than holding a request open, so a restart doesn't lose track of in-flight documents.

Troubleshooting

Symptom Cause / fix
401 Invalid API key / Authentication required The key is missing or wrong, it was regenerated, or it belongs to a different DIP environment. Send it in the x-api-key header.
429 Too many failed API key attempts 20 bad keys from your public IP within 60 s blocks that IP for the rest of the window.
429 (general) 100 requests per 60 s per public IP. Poll less often, or spread load.
403 group_id does not match the API key's group Remove group_id from the upload, or use the matching key.
403 on GET /api/workflows groupId is not the key's group.
404 Workflow not found: slug "…" The slug doesn't exist in the key's group in this environment. List the available workflows with GET /api/workflows (Step 3).
400 model_id is required… The workflow has no default model, so pass model_id.
413 / body too large The JSON body is over 50 MB (about a 37 MB file).
422 conversion_failed / password_protected The file couldn't be converted. Upload an unlocked or valid file.
504 / gateway timeout on upload A large file took longer than the route timeout. Retry with a smaller file, or ask the DIP team.
410 Gone on /view or /download The file was purged per the workflow's retention policy. Use /ocr for the result.
Document stays at pre_ocr / ongoing_ocr for a long time A DIP-side processing problem. Send the DIP team the document.id.
400 with a database/Prisma error message A DIP-side deployment problem. Report it to the DIP team.
Browser fetch blocked by CORS Expected. Call DIP from your backend.

Security Checklist

  • Keep the API key server-side only, in a secret store or environment variable. Never put it in front-end code or commit it.
  • The key acts for the whole group. Anyone who has it can read, upload, and delete that group's documents.
  • Use a separate key and group per environment. Never reuse a production key in dev/test.
  • Rotate the key with Settings → Regenerate key, then update your secret store. The old key stops working immediately, so plan the switch to avoid downtime.
  • Always use HTTPS, and don't turn off certificate verification in your HTTP client.
  • Don't log the x-api-key header, base64 file content, or OCR text if documents contain personal information.

Appendix: Trying This Against a Local DIP Instance

This applies only if you run DIP yourself for evaluation (for example from the DIP source repo). It is not part of a normal integration.

Local DIP setup notes
  • Use http://localhost:3002 as <DIP_API_URL>. The UI is at http://localhost:3000.
  • Seeding the DIP database (npm run db:seed) creates a test API key for the group seeddefaultgroup. The key's value is TEST_API_KEY in the DIP repo's .env.
  • If documents stay at ongoing_ocr, the Temporal worker isn't running. In the DIP repo, run npm run dev:temporal-worker.
  • If uploads fail with table … does not exist, the database is behind on migrations. Run npm run db:migrate in apps/backend-services.
